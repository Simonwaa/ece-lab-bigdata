# Lab 2 – Object storage with S3: answers

## During the lab

**ETag vs `md5sum`:** For a single upload, the ETag is the MD5 of the file, so it matches `md5sum`. For a multipart upload, the ETag is built from the hashes of the parts and ends with `-<number of parts>` (here `-25`), so it does not match.

**Bucket policy (is the deletion denied?):** Write what you saw. If `rm` worked, the policy did not apply to your user (some S3 servers apply bucket policies only to anonymous users). If you got `AccessDenied`, the policy worked.

## Questions

1. **Secret vs ConfigMap?** A ConfigMap stores plain text that anyone with read access can see. A Secret has its own access rules, is hidden in `kubectl describe`, and can be encrypted at rest. So we keep credentials separate from normal configuration.

2. **Job run again tomorrow? Production?** The credentials are temporary, so tomorrow they are expired and the Job fails (`ExpiredToken`). We must create new credentials and update the Secret. In production, we avoid copied credentials: the pod gets a role through its service account (for example IRSA on EKS or Workload Identity), or a secrets manager like Vault gives short-lived credentials automatically.

3. **Daily ingestion?** Use a Kubernetes `CronJob` with a `schedule` (for example `0 2 * * *`) and the same pod template. Set `concurrencyPolicy: Forbid` to avoid two runs at the same time. Make the job idempotent, for example by writing to a path with the date (`bronze/orders/date=2026-11-06/`), so a retry does not create duplicates.
